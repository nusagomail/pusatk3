# ADR 0019: Halaman direktori SSR dan akses web → API

Status: diterima · 26 November 2026 · issue #24 (PR pertama: `/cari`). Melanjutkan ADR 0010 dan 0018.

## Keputusan
- **Halaman direktori dirender saat diminta (SSR)**: `/cari`, `/jadwal/[id]`, `/penyedia/[slug]`, dan sejak #25 **beranda** (`/`): 4 jadwal terdekat, jumlah sertifikasi per bidang, dan kota dari API. Setiap bagian beranda punya cadangan (daftar statis / pesan), sehingga beranda tetap tampil bila API gagal; halaman yang tidak lengkap diberi `no-store`. Jadwal contoh yang dulu ditulis di kode (`SAMPLE_SCHEDULES`) dihapus. Halaman 404 tetap prerender (dipakai juga untuk tes CSP build).
- **Web membaca API lewat service binding `API`** saat di-deploy. Jalur ini internal di Cloudflare dan tidak melewati internet publik. Staging: `pusatk3-api-staging`. **Production belum diberi binding**: menambah binding production butuh persetujuan pemilik (CLAUDE.md) dan masuk checklist `/siapkan-rilis`. Tanpa binding, halaman menampilkan pesan "sedang tidak bisa dimuat" (503), bukan error.
- **Lokal (`pnpm dev`, e2e) memakai HTTP ke API lokal** (`API_ORIGIN = http://127.0.0.1:8787`, hanya di konfigurasi tingkat atas). Service binding antara dua proses `wrangler dev` (dev registry) terbukti tidak stabil ("Network connection lost"). `API_ORIGIN` tidak diwariskan ke staging/production (vars per environment), dan tesnya ada di `tests/wrangler-config.test.ts`.
- **`assets.run_worker_first: ["/", "/cari", "/jadwal/*", "/penyedia/*"]`**: dengan `not_found_handling: "404-page"`, navigasi browser ke path yang bukan file statis langsung mendapat `404.html` tanpa menjalankan Worker. Jalur SSR harus didaftarkan di sini.
- **Middleware Astro** (`apps/web/src/middleware.ts`) memasang header keamanan yang sama dengan `public/_headers` pada respons SSR, karena `_headers` hanya berlaku untuk aset statis. Middleware juga memasang `frame-ancestors 'none'`, `X-Robots-Tag: noindex, nofollow` di luar production, dan `Cache-Control` (`s-maxage=300`, `stale-while-revalidate=600` bila sukses; `no-store` bila gagal).
- **Parameter halaman di-whitelist** (`src/lib/search-params.ts`) sebelum diteruskan ke API, dengan urutan tetap. `utm_*`/`fbclid` diabaikan. Isian yang tidak valid menghasilkan pesan di halaman (400), bukan error.
- **Konfigurasi hasil build pindah ke `dist/server/wrangler.json`** sejak ada halaman SSR. Ikut diperbarui:
  - hook pengaman (mengecek `dist/server` dan `dist/client`);
  - pengecekan nama worker di Workers Builds staging (ADR 0015);
  - `deploy-production.yml`;
  - e2e.

## Konsekuensi
- **Cache CDN belum efektif.** Header `s-maxage` saja tidak menyimpan respons Worker (ADR 0010), dan Cache API tidak tersedia di `*.workers.dev`. Setiap kunjungan staging memanggil API. Cache API dan purge dikerjakan di #29 setelah ada domain.
- Halaman SSR baru wajib ditambahkan ke `run_worker_first` (dijaga tes konfigurasi).
- **Rate limit berbasis IP di API tidak bisa melihat IP pengunjung** untuk request dari web lewat service binding (semua datang dari Worker web). Rate limit halaman dipasang di Worker web, atau web meneruskan `CF-Connecting-IP` lewat header internal yang hanya dipercaya API bila datang dari binding (#28/#29; checklist `/siapkan-rilis`).
- Log staging (observability aktif) kini memuat URL `/cari` termasuk kata kunci pencarian. Tidak ada data pribadi yang diminta di halaman ini; tetap diperhatikan saat form lead (#28) dibuat.
- Perbaikan ikutan: `_headers` non-production sebelumnya berisi dua blok `/*`, dan blok kedua (noindex) membuat header keamanan halaman statis hilang di staging. Kini noindex disisipkan ke blok `/*` yang sama, dan tes build menolak blok ganda.
- e2e mengisi D1 lokal dengan data contoh (`pnpm db:migrate:local && pnpm db:import:local`) sebelum build dan tes. Jadwal contoh bertanggal Januari–Maret 2027 dan harus diperbarui sebelum itu, agar staging dan e2e tetap punya jadwal yang akan datang.
- **Detail jadwal `/jadwal/[id]` (PR kedua #24):** id selain ULID atau tidak ditemukan → 404 dengan halaman "Jadwal tidak ditemukan"; API gagal → 503. Tombol WhatsApp langsung ke `wa.me` sampai pencatatan lead (#28) memasang endpoint pengalihan; data contoh tidak punya kontak dan menyebutnya. "Kirim pertanyaan" menyusul di #28, "Simpan" setelah akun (Fase 2/5). Legalitas: kedaluwarsa diberi label, penyedia belum terverifikasi diberi catatan. JSON-LD `Course` (offer di tingkat Course, `CourseInstance` dengan `courseWorkload`) + `BreadcrumbList`; data contoh tidak mendapat JSON-LD Course dan diberi `noindex`. Jadwal yang sudah dimulai/berakhir diberi label, tombol WhatsApp diganti "Lihat jadwal lain", dan tanpa `offers`. Penyedia terverifikasi dengan izin kedaluwarsa tetap mendapat catatan (badge tidak dicabut otomatis; kebijakan pencabutan diputuskan di Fase 2). **Pencatatan klik WhatsApp sebagai lead (#28) wajib sebelum halaman ini dirilis ke production** (checklist `/siapkan-rilis`).
- **Profil penyedia `/penyedia/[slug]` (PR ketiga #24):** kepala profil (jenis, kota, badge hanya dari verifikasi, deskripsi, WhatsApp, situs sebagai tautan `nofollow`), bagian Jadwal/Legalitas/Cabang lewat tautan jangkar (tanpa JavaScript), catatan "PusatK3 tidak memproses pendaftaran maupun pembayaran". Ulasan (Fase 5), klaim/koreksi profil (Fase 2), logo (unggah R2, Fase 2) dan "Minta penawaran in-house" (form lead, #28) belum ada; halaman menyebut klaim "segera tersedia". Skema output API hanya meloloskan situs `https` (`contactSchema.website`), sehingga tautan `javascript:` tidak pernah sampai ke halaman. JSON-LD `Organization` hanya untuk data asli; data contoh `noindex`.
